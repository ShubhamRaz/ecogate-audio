# Experimental Validity Checklist

Use this checklist before generating any publication-facing result.

## Data provenance

- [ ] Start with a clean, empty `data/raw/` directory before mounting the authoritative archive.
- [ ] Confirm `.ecogate_synthetic_reference_fixture` is absent.
- [ ] Confirm annotation records correspond to the actual archive and class labels have been manually inspected.
- [ ] Record archive DOI/version, download date, file count, file hashes, and annotation version.
- [ ] Re-run the audit and inspect `dataset_source_type`; it must not be `synthetic_reference_fixture`.
- [ ] Review the difference between the reported archive count and the new local count. Do not reuse the historical 8,663/8,512 values.
- [ ] Keep unknown source/session IDs as unknown; do not claim geographic or temporal independence when metadata are missing.

## Splits and leakage

- [ ] Recreate the split manifest after the source archive has been audited.
- [ ] Confirm duplicate waveform hashes, explicit source IDs, and explicit session IDs are disjoint across partitions.
- [ ] Inspect group sizes and class balance in every partition.
- [ ] Ensure all preprocessing statistics are fitted on training samples only.
- [ ] Ensure OOF base-model folds use connected duplicate/source groups.
- [ ] Ensure benefit estimator training, open-set threshold calibration, temperature scaling, and final test evaluation use their intended disjoint partitions.
- [ ] Never select thresholds, architectures, or hyperparameters on final test labels.

## Model architecture

- [ ] Treat current `LightweightStudentCNN` and `StrongExpertAudioModel` as compatibility names for handcrafted/fixed-feature models, not actual CNN/AST architectures.
- [ ] For a CNN/AST claim, implement a genuinely trainable backbone, document all trainable/frozen parameters, and retrain from scratch.
- [ ] Report seeds, optimizer, learning rate, batch size, epochs, validation selection, parameter count, and checkpoint hash.
- [ ] Compare against a strong classical baseline and appropriate external/pretrained models without data leakage.

## Routing

- [ ] Train benefit estimation only from group-held-out predictions.
- [ ] Calibrate the threshold on the calibration partition only.
- [ ] Respect the lower of configured call-rate limit, energy-derived call-rate limit, and any requested target cap.
- [ ] Evaluate actual pre-expert invocation masks; never use expert outputs to decide whether the expert should have been invoked.
- [ ] Report actual call rate, loss, compute cost, and group-level uncertainty.
- [ ] State that a constant per-call expert cost cannot alter sample ranking at a fixed call budget. For variable-cost claims, measure/document per-sample cost or impose a justified variable constraint.
- [ ] Keep test-loss oracle policies labelled non-deployable upper bounds.

## Metrics and selective prediction

- [ ] Recompute ROC-AUC, average precision, FPR95, calibration, and open-set metrics with a documented positive class and score direction.
- [ ] Use calibration thresholds for operational metrics, not test-optimized thresholds.
- [ ] Compute risk–coverage from the actual routed prediction, its own confidence, and its actual loss.
- [ ] Report macro and per-class metrics with support counts.
- [ ] Use connected-group bootstrap or a documented alternative for confidence intervals.

## Deployment and efficiency

- [ ] Distinguish compressed INT8 weight storage from integer-only inference. Current code dequantizes to float32.
- [ ] Use an actual integer runtime before claiming INT8 inference acceleration.
- [ ] Derive MAC/FLOP counts from operator-level execution, not parameter-count multiplication.
- [ ] Benchmark on the named target device with fixed input lengths, warm-up, repeat count, CPU affinity/power mode, and software versions.
- [ ] Measure electrical joules with an external meter or mark power as not measured.
- [ ] Physically test Raspberry Pi Zero 2 W latency, memory, thermal behavior, and power before making device suitability claims.

## Release gate

- [ ] GitHub Actions passes on supported Python versions.
- [ ] Full integration tests pass on the actual dataset.
- [ ] Full pipeline runs from a clean environment with hashes and logs archived.
- [ ] All reports and plots were generated by the corrected code and have a run ID/config/data-manifest hash.
- [ ] Manuscript, abstract, conclusion, and claims match the measured results and limitations.
